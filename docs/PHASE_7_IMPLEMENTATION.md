# Phase 7 — Product & Service Management

Implementation notes, scoped to the brief: a clean, authoritative Product/Service catalog with module management, evolving the Phase 2 `Product`/`ProductModule` registry rather than replacing it. No subscriptions, billing, contracts, client portal, or reporting — see `docs/PRODUCT_CATALOG_ARCHITECTURE.md` and `docs/PRODUCT_MODULE_ARCHITECTURE.md` for the architecture and `docs/PHASE_7_COMPLETION_REPORT.md` for status.

## What changed, and why

### 1. Inspection findings — Phase 2 had the registry, not the CRUD
`Product`/`ProductModule` (Phase 2) had `id/code/name/description/status/version/configuration` and `id/productId/code/name/description/status`, respectively — a shape, no service/route/permission wired to it, and zero rows in any environment (verified via `psql` before touching the schema). `products.read/create/update/delete` already existed in `PERMISSION_KEYS` but only `products.read` was ever granted to any role — Phase 2 planned for this, Phase 7 completes it. Both existing commercial hooks (`Subscription.productId`, `SubscriptionItem.productModuleId`) were preserved untouched.

### 2. Database migration (`prisma/migrations/20260924000001_phase7_product_catalog/`)
Additive: `ProductType` enum (PRODUCT/SERVICE); `ProductStatus.DEPRECATED` renamed to `INACTIVE` (matching the brief's exact 4-value lifecycle: DRAFT/ACTIVE/INACTIVE/ARCHIVED — `DEPRECATED` had zero references anywhere in the codebase, confirmed by grep, so the rename is non-breaking); `ProductModuleStatus.DEPRECATED` renamed to `INACTIVE` the same way (module lifecycle: DRAFT/ACTIVE/INACTIVE); `Product` gained `type`, `slug` (unique), `shortDescription`, `isFeatured`, `displayOrder`, `createdById`/`updatedById`; `ProductModule` gained `slug` (unique per product), `displayOrder`, `isCore`. `slug`/`type` were added nullable-then-backfilled-then-`NOT NULL` (safe pattern, even though 0 existing rows were verified — defensive per the established Phase 5/6 migration-safety convention, in case this ever runs against a non-empty table). Verified as both an upgrade (`artify_dev`, `artify_test`) and from a from-scratch database (all 6 migrations in order).

### 3. Catalog ownership — platform-global, not organization-scoped
Per §8's decision tree: the existing `Product` model already had **no** `organizationId` and its own Phase 2 doc comment already said "none of these are hardcoded... rows created through this registry." That's the platform-global answer, preserved as-is — no `organizationId` was added. Catalog administration is gated entirely by permission (`products.create/update/archive`), never by a per-row ownership check, because there is no owning tenant to check against. See `docs/PRODUCT_CATALOG_ARCHITECTURE.md` for the full reasoning.

### 4. Backend additions (all additive, permission-gated, no schema duplication)
Repositories: `productRepository` (global lookups — `findById`/`findByCode`/`findBySlug`, no per-tenant scoping needed), `productModuleRepository` (`findByIdForProduct(id, productId)` is the only scoped lookup — never a bare `findById` when a product context is being asserted, matching the `findByIdInOrg` convention from Phases 5-6; a separate `findById` exists only for the flat `/product-modules/:id` routes, which take no second product id to cross-check against). Services: `productService`, `productModuleService`. Routes: `productRoutes` (`/products`, with nested `/products/:id/modules` and `/products/:id/modules/reorder`), `productModuleRoutes` (`/product-modules`, standalone get/update/archive). New permission keys: `products.read/create/update/archive`, `product_modules.read/create/update/archive/reorder` — `products.delete` (Phase 2, ungranted, unreferenced anywhere) was renamed to `products.archive` to match the brief's exact requested set rather than carrying both a "delete" and an "archive" permission for an operation that's never a physical delete.

### 5. Product lifecycle
`DRAFT → ACTIVE → INACTIVE ↔ ACTIVE`, `DRAFT|ACTIVE|INACTIVE → ARCHIVED` (terminal), validated server-side (`productService.assertValidTransition`). `ARCHIVED` is reachable only through the dedicated `POST /products/:id/archive` endpoint (permission: `products.archive`) — a generic `PATCH .../status=ARCHIVED` is rejected with a 400 naming the correct endpoint, the same pattern Phase 5 used for `Lead.CONVERTED`. Once archived, a product rejects further edits (409) but is never physically deleted — `Subscription.productId` always resolves.

### 6. Product code, slug, and duplicate protection
`code` is normalized (trimmed, uppercased, `[A-Za-z0-9._-]+` only) and globally unique (`@unique` — the catalog is global, so "unique within scope" means unique full stop). `slug` is server-generated by default (from `name`, collision-safe via `productRepository.findUniqueSlug`'s suffix loop) or caller-supplied and validated (`^[a-z0-9-]+$`). Both duplicate checks happen at the service layer before insert *and* the underlying DB unique constraints are the real backstop — a race caught via `Prisma.PrismaClientKnownRequestError` code `P2002` is folded into the same clean `409`, proven by two dedicated concurrency tests (duplicate code, duplicate explicit slug) that fire real concurrent HTTP requests.

### 7. Product modules
Every module belongs to exactly one product (`productId`, FK `onDelete: Cascade` — unchanged from Phase 2, now effectively theoretical since a product is never physically deleted post-Phase-7). `code`/`slug` are unique **per product** (`@@unique([productId, code])`, `@@unique([productId, slug])`), not globally — proven by a test that creates the same code under two different products successfully. Module "archive" (§14 — the module lifecycle has no separate ARCHIVED state, only DRAFT/ACTIVE/INACTIVE) sets status to `INACTIVE`, never a physical delete — `SubscriptionItem.productModuleId` always resolves.

### 8. Reordering (§13/§36) — transactional, cross-product-safe
`POST /products/:id/modules/reorder` takes the full ordered array of module ids. `productModuleService.reorderModules` first validates the request is **exactly** the product's current module set (no missing id, no extra id, no duplicate) — a request naming a module from a different product fails this set-equality check immediately (400), before any write. The actual reorder (`productModuleRepository.reorder`) applies every `displayOrder` update inside one `prisma.$transaction`, using Prisma's extended-where-unique feature (`{id, productId}`) as a second guard: even if the set-equality check were ever bypassed, an update whose `productId` doesn't match would throw and roll back the whole transaction, never partially applying.

### 9. Frontend
`src/lib/api.ts` gained `productsApi`/`productModulesApi` (the shared `paginatedGet` helper's params type was widened to accept `boolean`, for the `isFeatured` filter — a small, safe, backward-compatible change). `NavItem.section` gained `"Products"`, with two nav entries (`All Products`, `Product Modules`) both rendering the same `ProductsPage` component — matching the `Onboarding`/`Workspaces` precedent from Phase 6 (a genuinely separate cross-product module list has no backing endpoint and would be fabricated data, so it isn't built). `ProductsPage` is a master-detail list (matching `ClientsPage`/`WorkspacesPage`) with modules managed entirely within the selected product's detail pane: add/activate-deactivate/archive, plus up/down reorder buttons that recompute and submit the full order to the real backend endpoint (no drag-and-drop dependency introduced; the backend remains the sole source of truth for order, and a failed reorder reloads the real state rather than trusting the optimistic local reorder).

### 10. Two pre-existing tests updated for an intentional permission change
`tests/integration/auth.test.ts` and `tests/security/authz.test.ts` both encoded a Phase 2-era assumption ("ADMIN is not the platform-catalog role," using `products.create` as an example of a permission ADMIN lacks). Phase 7 intentionally grants `products.*`/`product_modules.*` to ADMIN (§21/§22 — "product catalog administration should be controlled by appropriate platform permissions," consistent with ADMIN already administering CRM/onboarding/workspaces in full). Both tests were updated to assert the new, correct behavior and to use `roles.create` (genuinely still SUPER_ADMIN-only — role management itself) as the example permission ADMIN lacks, rather than treating the change as a regression to work around.

### 11. Deliberate Phase 7 scope boundaries
No subscription, billing, contract, invoice, pricing, or commercial-relationship logic was built or wired. `Subscription.productId`/`SubscriptionItem.productModuleId` were left exactly as Phase 2 defined them — Phase 7 only had to keep the catalog they point at compatible, not build on them. `artifysolscom` was not touched — the catalog is Control Center/admin-facing only; no public pricing or subscription pages were added.
