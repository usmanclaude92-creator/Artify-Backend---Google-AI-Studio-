# Phase 2 — Database Architecture, Supabase PostgreSQL & Core Data Model

Implementation notes for Phase 2, scoped exactly to the Phase 2 brief: database architecture and the core data model, not business logic (CRM/CMS/billing UI, client onboarding, AI automation — those stay out of scope, per the brief's own final rule). For the outcome/status report, see `docs/PHASE_2_COMPLETION_REPORT.md`. For connection/migration procedure, see `docs/SUPABASE_DATABASE_SETUP.md`. For the as-built schema, see `docs/DATABASE_SCHEMA.md`.

## What changed, and why

### 1. Starting point (verified before changing anything, per the brief's first instruction)
Phase 1 had shipped a real Prisma/Postgres identity + webhook foundation: `companies`, `users`, `sessions`, `audit_logs`, `webhook_events`, with `users.permissions` as a flat array (no `roles`/`permissions` tables). This was confirmed by reading `prisma/schema.prisma`, `git log`, and running the existing test suite (58 passing) before any Phase 2 change — not assumed from the Phase 1 report alone.

### 2. Schema (`prisma/schema.prisma`, 30 application tables across 9 domains)
Extended, not replaced: Identity/Security gained `organizations` (renamed from `companies`, `ADR-010`), `organization_memberships`, `roles`, `permissions`, `role_permissions` (`ADR-011`) — `sessions`/`audit_logs`/`webhook_events` kept their shape with field renames (`company_id` → `organization_id`). Seven new domains were added from scratch, schema-only: CRM (`leads`, `clients`, `contacts`), Products (`products`, `product_modules`), Commercial (`contracts`, `subscriptions`, `subscription_items`, `invoices`, `invoice_items`), CMS (`pages`, `posts`, `categories`, `tags`, `authors`, `content_revisions`, `post_tags`), Media (`media_assets`), Notifications (`notifications`, `notification_preferences`), Configuration (`system_settings`). See `docs/DATABASE_SCHEMA.md` for the full column-level documentation and ER diagrams.

### 3. Migration
One migration, `prisma/migrations/20260920000001_phase2_core_data_model/`, generated non-interactively (`prisma migrate diff --from-migrations ... --to-schema-datamodel ... --shadow-database-url ... --script`, since `prisma migrate dev` refuses non-interactive execution — see `ADR-013`), then hand-reviewed and hand-extended with `CHECK` constraints Prisma's schema DSL has no syntax for: non-negative monetary/quantity values, date-range sanity (`end_date >= start_date`, `due_date >= issue_date`), and the `content_revisions` exactly-one-parent constraint (`num_nonnulls(page_id, post_id) = 1`) replacing an unsafe polymorphic-FK pattern. One destructive operation (`DROP TABLE companies`, superseded by `organizations`) — verified empty in every environment it ran against before applying. Applied via `prisma migrate deploy` to a from-scratch local `artify_dev`/`artify_test` (dropped and recreated clean first), never `db push`, never against a database assumed-but-not-confirmed empty.

### 4. Application code rework (identity domain only — the domain that already had routes/services)
- `server/types/domain.ts`: `SYSTEM_ROLE_KEYS` (`SUPER_ADMIN`/`ADMIN`/`MANAGER`/`USER`/`VIEWER` — a deliberate replacement of Phase 0/1's ad-hoc role set, not a preservation of it, per the brief), `PERMISSION_KEYS` (~40 namespaced permissions), `ResolvedRole`, `sanitizeUser`.
- `server/repositories/`: `organizationRepository.ts` (new, replaces `companyRepository.ts`), `roleRepository.ts` (new — `resolveById()` joins `role_permissions` → `permissions` at read time), `userRepository`/`sessionRepository`/`auditLogRepository`/`webhookEventRepository` updated for the renamed/restructured fields.
- `server/utils/crypto.ts`: `hashToken()` (SHA-256) — `sessions.token_hash` replaces storing the raw bearer token, so a leaked row can't be replayed as a session.
- `server/services/authService.ts`: `register()` now creates `Organization` + `User` + `OrganizationMembership` in one transaction (previously `Company` + `User`); role resolved via `roleRepository` instead of read off the user row.
- `server/middleware/auth.ts`: `req.companyId` → `req.organizationId` throughout; permission checks now read `req.user.role.permissions` (data-driven) instead of a hardcoded per-user array.
- `server/routes/v1/systemRoutes.ts`: new `GET /system/database` (SUPER_ADMIN-only) reporting migration status and table counts — no connection string, no credentials, verified by a test asserting the raw response body contains no `postgresql://` substring and no case-insensitive `password` substring.

### 5. Seed data (`prisma/rolePermissionSeed.ts`, `prisma/seed.ts`)
Role/permission definitions extracted into a shared module used by both the dev seed script and the test setup, so tests and local dev never drift. `seed.ts` creates Artify's own internal organization and exactly one bootstrap SUPER_ADMIN user, read from `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD` — no hardcoded default password; the script throws if the env vars are unset, rather than silently seeding a guessable credential.

### 6. Tests
20 new tests: `tests/integration/schemaConstraints.test.ts` (11 — direct-Prisma tests bypassing the service layer entirely, proving the database itself rejects bad data even if the API were bypassed: duplicate email/slug/permission-key/role-permission/membership, FK violation, negative monetary CHECK, bad date-range CHECK, content-revision orphan CHECK, exact decimal precision, transaction rollback) and `tests/security/rbacAndAudit.test.ts` (9 — RBAC is data not code, SUPER_ADMIN has every permission, audit records survive actor deletion with `actor_user_id` set NULL, tenant-isolation query proof, session expiry/revocation). Existing Phase 1 tests (`auth.test.ts`, `authz.test.ts`, `health.test.ts`) updated for the renamed fields and extended for the new role/permission shape. `tests/helpers/db.ts`'s `resetDb()` rewritten for the full new table set and FK order, deliberately leaving `roles`/`permissions`/`role_permissions` untouched as persistent reference data. Full suite: **81 tests passing, 10 files, 0 failing** (verified this session against a real local Postgres, not mocked).

### 7. Documentation
Eight new ADRs (`ADR-008` through `ADR-015` — Supabase as production DB, Prisma as sole access layer, multi-tenant org model, permission-based RBAC schema, financial decimal precision, migration strategy, connection pooling, RLS-vs-backend-boundary), `docs/DATABASE_SCHEMA.md` (as-built schema reference), `docs/SUPABASE_DATABASE_SETUP.md` (connection/migration procedure, no credentials). Six existing docs updated with a "Phase 2 update" callout reflecting what changed: `DATABASE_DESIGN.md`, `TARGET_ARCHITECTURE.md`, `API_DESIGN.md`, `AUTHORIZATION_MODEL.md`, `SECURITY_MODEL.md`, `PRODUCTION_READINESS_CHECKLIST.md` (checkboxes updated to genuinely-true state, not aspirationally).

### 8. Deliberate Phase 2 scope boundaries
Per the brief's non-goals: no CRM/CMS/Commercial service or route layer was built (schema only — those tables have no repository, no service, no `routes/v1/*` mount); no session-switching between an `OrganizationMembership`'s multiple orgs (still one "home org" per session, per Phase 1); no Row Level Security (evaluated and explicitly not enabled, `ADR-015`); no `DIRECT_DATABASE_URL` (reasoned out as unneeded for the current single-long-lived-process deployment shape, `ADR-014`); no speculative tables beyond the brief's field lists (e.g. no `opportunities`/`api_keys`/AI-coworker tables — those stay out until a real phase needs them).

## Supabase connectivity — BLOCKED (environmental, not code)
This session's execution sandbox could not reach the designated Supabase project (`cfkymotcnccgvkpmcevp`) at all: a raw TCP probe to its Postgres port timed out, and a plain HTTPS request to `supabase.com` itself was rejected by the sandbox's own egress proxy with a 403. This is a property of this execution environment, not of the code — `server/config/env.ts` and `prisma/schema.prisma` are provider-agnostic, and the schema/migration/constraints were built and fully verified against a local Postgres instance that mirrors the target exactly (same engine, same schema, same `CHECK` constraints). Per the brief's own explicit instruction for this scenario, this is reported plainly rather than worked around or faked. See `docs/SUPABASE_DATABASE_SETUP.md`'s "Known limitation" section and `docs/PHASE_2_COMPLETION_REPORT.md`'s "Supabase Verification" section for exactly what was and wasn't verified.

## Credential handling (verbatim requirement honored)
The real Supabase database password was never written into source code, committed, placed in documentation, printed in a persisted log, or included in any file that will be committed. It existed only transiently in shell command arguments and in two gitignored local files (`.env`, `.env.test`), both of which were overwritten with local-Postgres-only values once the connectivity block was confirmed. A repo-wide credential sweep (grep for connection-string and known-value patterns across every file about to be committed) was run before this phase's commit and found nothing beyond the documented placeholder template in `docs/SUPABASE_DATABASE_SETUP.md` (`postgresql://postgres.<project-ref>:<PASSWORD>@...`).
