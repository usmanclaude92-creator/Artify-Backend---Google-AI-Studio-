# Phase 6 — Client Onboarding & Workspace Provisioning

Implementation notes, scoped to the brief: the workflow that converts a CRM Client into an operational Artify workspace — onboarding lifecycle, workspace provisioning, client-administrator invitations, and the Control Center UI for all three — built entirely on the Phase 1-5 foundation. No product catalog, subscriptions, billing, CMS, media, AI, external integrations, or client-portal business modules. See `docs/CLIENT_ONBOARDING_ARCHITECTURE.md` and `docs/WORKSPACE_PROVISIONING.md` for the architecture and `docs/PHASE_6_COMPLETION_REPORT.md` for status.

## What changed, and why

### 1. Inspection findings — the Organization model already IS the workspace
`Organization` (Phase 2) already has everything a "workspace" needs: `type` (CLIENT/INTERNAL/PARTNER), `status` (ACTIVE/TRIAL/SUSPENDED/ARCHIVED), `timezone`, `currency`, `email`/`phone`/`website`/`address`, and its own `OrganizationMembership`/`Role`/`Session` machinery. Building a second "Workspace" table would have been exactly the parallel-architecture the brief prohibits (§4/§34). Instead, a workspace is simply an `Organization` row (`type: "CLIENT"`) linked 1:1 to a `Client` via a new `Client.workspaceOrganizationId` — see `docs/WORKSPACE_PROVISIONING.md`. The only schema gap was `locale` (added to `Organization`) and the onboarding/invitation records themselves, which had no Phase 2 equivalent.

### 2. Database migration (`prisma/migrations/20260923000001_phase6_onboarding_workspace/`)
Purely additive: `Organization.locale` (default `"en"`), `Client.workspaceOrganizationId` (nullable, `@unique` — enforces at most one workspace per client at the DB level, §5), `OnboardingStatus` enum, `ClientOnboarding` model, `WorkspaceInvitation` model. One hand-added partial unique index, `workspace_invitations_one_pending_per_email` (`WHERE accepted_at IS NULL AND revoked_at IS NULL`) — Prisma's DSL can't express a filtered unique constraint; same technique Phase 5 used for `contacts_one_primary_per_client`. Verified as both an upgrade (`artify_dev`, `artify_test`) and from a from-scratch database (all 5 migrations in order).

### 3. Workspace lifecycle reuses `OrganizationStatus` — no new enum
Per §6's "use an existing enum if already present": `TRIAL` = PENDING (just provisioned, not yet active), `ACTIVE` = ACTIVE, `SUSPENDED` = SUSPENDED, `ARCHIVED` = DEACTIVATED. Documented directly in `schema.prisma` and `docs/WORKSPACE_PROVISIONING.md`. Transitions are validated server-side (`workspaceService.assertValidWorkspaceTransition`) — `TRIAL→ACTIVE→SUSPENDED↔ACTIVE→ARCHIVED(terminal)`, never an arbitrary jump.

### 4. Onboarding is independent of workspace status (§7)
`ClientOnboarding` (`NOT_STARTED/IN_PROGRESS/READY/COMPLETED/CANCELLED`) has no foreign key to workspace status and never touches `Organization.status`. A workspace can be `ACTIVE` while onboarding is still `IN_PROGRESS`, or `TRIAL` while onboarding is `READY` — both states are independently queryable and independently mutated.

### 5. Onboarding checklist — JSON, not a child table
The 7-stage checklist (§8: Client Verified, Workspace Created, Primary Contact Confirmed, Administrator Invited, Administrator Accepted, Workspace Configured, Onboarding Completed) is stored as a `Json` array on `ClientOnboarding.checklist`, not a separate table — extensible (new stages need no migration) and avoids a needless join for what's fundamentally one record's sub-state. `currentStep` is denormalized alongside it (the first incomplete item's key) so list views don't need to re-parse the JSON per row. Server-computed only; the frontend never infers or stores checklist state itself (§8's "not only in localStorage").

### 6. Backend additions (all additive, tenant-scoped, permission-gated)
Repositories: `clientOnboardingRepository`, `workspaceRepository`, `workspaceInvitationRepository` — `workspaceRepository`'s only lookup method is `findByIdForOwner(id, ownerOrganizationId)`, scoped through the `provisionedForClient` relation, matching the `findByIdInOrg` convention from Phases 4-5. Services: `onboardingService`, `workspaceService`, `invitationService`. Routes: `onboardingRoutes` (`/onboarding`), `workspaceRoutes` (`/workspaces`, with nested `/workspaces/:id/members` and `/workspaces/:id/invitations`), `invitationRoutes` (`/invitations` — authenticated revoke plus two deliberately public endpoints, `GET /invitations/:token` and `POST /invitations/:token/accept`), and two routes nested under the existing `clientRoutes` (`POST /clients/:clientId/onboarding/start`, `POST /clients/:clientId/workspace/provision`) matching Phase 5's contacts-nesting convention. New permission keys: `onboarding.read/create/update/complete`, `workspaces.read/create/update/suspend`, `invitations.read/create/revoke`.

### 7. Workspace provisioning (transactional, race-safe)
`workspaceService.provisionWorkspace()` runs inside one `prisma.$transaction`: creates the `Organization`, links it via a **conditional** `updateMany` (`WHERE workspaceOrganizationId IS NULL`), auto-creates a `ClientOnboarding` record if none exists yet, and marks `WORKSPACE_CREATED` complete on it. Two failure modes are both caught and turned into a clean `409 ConflictError` rather than a raw database error: the conditional-update losing the race (checked inside the transaction, mirroring `leadService.convertLead`'s pattern from Phase 5), and the workspace's own unique `slug` colliding under true concurrency (caught via `Prisma.PrismaClientKnownRequestError` code `P2002` around the transaction, since the slug-uniqueness pre-check itself happens outside the transaction and can't be made atomic against a second in-flight request). Verified directly by a concurrency test — two simultaneous provisioning calls for the same client produce exactly one workspace, one 201, one clean 409.

### 8. Client-admin invitations (§18-23)
The invited role is a fixed constant (`"ADMIN"`), never read from the request — the create-invitation schema doesn't even accept a role field, eliminating the entire "arbitrary role assignment" attack surface (§19/§20) rather than validating it after the fact. Token handling mirrors `PasswordResetToken` exactly: `art_invite_...` raw token, SHA-256 hash at rest, never logged, a `devToken` returned only outside production (same `authService.requestPasswordReset` convention, Phase 13 integration point for real email delivery). No stored status enum — `PENDING/ACCEPTED/REVOKED/EXPIRED` is computed from `acceptedAt`/`revokedAt`/`expiresAt` at read time (`invitationService.computeInvitationStatus`), avoiding a second source of truth. Acceptance (`invitationService.acceptInvitation`) is transactional and race-safe the same way provisioning is: a conditional `updateMany` on the invitation row, plus a caught `P2002` on `User.email` for the case where two concurrent acceptances of a brand-new invitee's email both pass the pre-transaction "does this user exist" check before either commits.

### 9. Existing vs. new invited users (§22/§23)
`acceptInvitation` checks `userRepository.findByEmail` before the transaction: an existing identity gets only a new `OrganizationMembership` in the target workspace (no duplicate `User` row, no touched password); a new identity gets a `User` created with the invitation's fixed role and a password supplied at acceptance time (validated through the existing `validatePasswordPolicy`), never a default/weak credential.

### 10. Frontend
`src/lib/api.ts` gained `onboardingApi`, `workspacesApi`, `invitationsApi` (the last two public preview/accept calls pass `suppressUnauthorizedHandling`, matching the login/register convention — a 401 there means "bad invitation," not "your session expired"). `NavItem.section` gained `"Onboarding"` and `"Workspaces"`, each with two nav entries per the brief's own structure (`Overview`/`Pending Onboarding`, `All Workspaces`/`Members`) — `Pending Onboarding` and `Members` intentionally render the same components as their siblings (`OnboardingPage` reads its own path to default the status filter; a genuinely separate cross-workspace members view has no backing endpoint and would be fabricated data, so it isn't built). New pages: `OnboardingPage` (read-only queue + checklist detail), `WorkspacesPage` (master-detail with embedded members/invitations, matching the `ClientsPage`/`OrganizationsPage` precedent), `AcceptInvitationPage` (public, token read from the URL query string like `ResetPasswordPage`). `ClientsPage`'s client detail gained an "Onboarding & Workspace" section showing the backend-computed `provisioningStatus` badge and permission-gated actions (Start onboarding, Provision workspace, Invite administrator, Complete onboarding, Suspend workspace) — matching §28 exactly.

### 11. Public invitation-acceptance route
`App.tsx` gained a `PUBLIC_PATHS` check (`/accept-invitation`) evaluated before the existing authenticated/unauthenticated branching, since an invitee typically has no session and an already-authenticated user (accepting a second workspace) must also reach it without being redirected away. `AuthContext` gained `setSessionFromAcceptedInvitation` — applies the session the accept call already returned, without a second login round-trip.

### 12. Deliberate Phase 6 scope boundaries
No product catalog, subscriptions, billing, invoices, CMS, media, AI automation, notifications/integrations, reporting, or full client-portal business modules were built or wired, in either repo. `artifysolscom` was not touched — onboarding/provisioning is Control Center/admin-facing only.
