# Phase 4 — Control Center Shell & System Administration

Implementation notes, scoped to the brief: an authenticated Control Center shell and System Administration modules (Users, Roles, Permissions, Organizations, Audit Log, Sessions, Settings) over the Phase 3 auth/RBAC backend. No CRM, CMS, Billing, Products, Media, Reporting, or AI. See `docs/CONTROL_CENTER_ARCHITECTURE.md` for the architecture and `docs/PHASE_4_COMPLETION_REPORT.md` for status.

## What changed, and why

### 1. Deleted (fabricated, unsalvageable without a backend behind it)
`src/context/AdminDataContext.tsx` (1182 lines — localStorage-backed state for every domain, `switchUserRole()` granting instant client-side privilege escalation), `src/data/seedData.ts`, `GovernanceControlModule.tsx`, `GlobalSearchModal.tsx`, `PublicWebsiteView.tsx` (this repo's job is the Control Center, not a second public site — `artifysolscom` owns that), and 17 demo "modules" (Leads/Products/Blog/Customers/Onboarding/Applications/Integrations/Notifications/Analytics/Reports/Seo/Subscriptions/AI/Website/Media/SystemHealth/old-Dashboard) whose entire content was fabricated data with no real backend to source from. Rebuilding any of them for real is explicitly out of Phase 4's scope (CRM/CMS/Billing/Products/AI/Media/Reporting).

### 2. Built new (Phase 4 scope only)
Auth: `AuthContext` (real, session-scoped), `LoginPage`/`ForgotPasswordPage`/`ResetPasswordPage` (real Phase 3 endpoints, no demo shortcuts). Shell: `AppShell`/`Sidebar`/`Header`, permission-aware via `lib/permissions.ts`'s extensible `NAV_ITEMS`. Modules: `DashboardPage` (real counts only), `UsersPage`, `RolesPage` (read-only — no role-CRUD backend exists), `PermissionsPage` (read-only catalog), `OrganizationsPage` (+ membership management), `AuditLogPage` (paginated, filtered, read-only), `SecurityPage` (self-service sessions), `SettingsPage` (thin CRUD over `system_settings`).

### 3. Backend additions (all additive, no schema change beyond Phase 3's `password_reset_tokens`)
`GET /organizations/:id/members`, `GET /organizations/:id/summary`, `GET /audit-logs`, `GET /auth/sessions`, `POST /auth/sessions/:id/revoke`, `GET /settings`, `PATCH /settings/:key` — each `authenticateToken` + `requirePermission` + tenant-scoped, per `docs/CONTROL_CENTER_ARCHITECTURE.md`. `auditLogQueryRepository.ts` is a deliberately separate module from `auditLogRepository.ts`, which must keep exposing exactly one method (`record`) per the existing append-only test invariant.

### 4. A real bug found and fixed during browser verification
`apiClient`'s auth-token getter originally read from React state via a `useEffect`-registered closure. `AuthContext.login()` set the token state and then immediately called `authApi.me()` — but React state commits asynchronously, so the very first authenticated request after login raced the effect and sometimes fired with the old (null) token, 401ing and incorrectly triggering the "session expired" flow on a user's first successful login. Fixed with a `useRef` mirror updated synchronously alongside the state (`docs/CONTROL_CENTER_ARCHITECTURE.md` "Authentication integration"). Caught by an actual Playwright run against the real app, not by unit tests alone — this is exactly the class of bug that only shows up when the real login → real request sequence is exercised end to end.

### 5. artifysolscom fabricated-auth removal (§4)
`AuthContext.login()`/`register()` now call the real backend and throw on failure. Removed: `loginAsDemo()`, the `demoKey` param, email-matches-demo-account auto-login, "Auto-fill demo credentials," and three "1-Click Demo Profile"/"1-Click Editor Demo" buttons across `AuthModal.tsx` and `CreateArticleModal.tsx` — the direct equivalent of the "Login as Admin"/"Demo Super Admin" pattern §9/§34 name explicitly. "Forgot password?" now calls the real reset-request endpoint instead of an `alert()`. Signup gained a required password field. The portal's subscription/billing/product screens remain local placeholder data post-login (unchanged from before, now accurately labeled) — real integration is Billing/Products/CRM phase work, explicitly out of scope here.

### 6. Deliberate Phase 4 scope boundaries
No CRM/CMS/Billing/Products/Media/Reporting/AI module was built or wired, in either repo. `RolesPage` and `PermissionsPage` are read-only because no role-CRUD or permission-CRUD backend endpoint exists (only `GET /roles`/`GET /permissions` from Phase 3) — inventing frontend mutation UI for a capability the API doesn't have would itself be a form of fabrication (§15: "the frontend must not invent authorization rules"). No cookie-based session or CSRF machinery was introduced — the Phase 3 bearer-token architecture was kept as instructed (§5).
