# ADR-008: Supabase PostgreSQL as the Production Database

## Status
Accepted (Phase 2)

## Context
`ADR-002-database.md` (Phase 0) already selected PostgreSQL as the production database technology, deferring the specific hosting provider. Phase 2's brief designates a specific Supabase project (`cfkymotcnccgvkpmcevp`) as the target. Supabase is a managed Postgres provider (plus auxiliary services — Auth, Storage, Realtime, autogenerated REST/GraphQL — that this project does not use, see `ADR-015`).

## Decision
Use the designated Supabase project's PostgreSQL instance as the production database. Supabase is consumed here strictly as **managed PostgreSQL infrastructure** — connected to exclusively through Prisma (`ADR-009`), never through Supabase's client SDK, Auth, or auto-generated APIs. This keeps the architecture exactly what `docs/TARGET_ARCHITECTURE.md` specifies:

```
Browser → Artify Platform API → Prisma → Supabase PostgreSQL
```

## Consequences
- Backups/PITR/scaling are the managed provider's responsibility — see `docs/SUPABASE_DATABASE_SETUP.md` for what's confirmed about the actual plan vs. what's assumed.
- Connection pooling must account for Supabase's pooler architecture (session vs. transaction mode) — see `ADR-014`.
- **Verification status (Phase 2, environmental limitation, not an architectural gap)**: this execution environment's network egress is allow-listed and does not reach the designated Supabase project — verified directly (a raw TCP probe to its Postgres port times out; a plain HTTPS request to supabase.com itself is rejected by the egress proxy with 403). All Phase 2 schema/migration work was built and verified against a local PostgreSQL instance instead; the schema and application code make no host-specific assumption, so this does not block adopting Supabase once a environment with the right network access applies the migrations. See `docs/PHASE_2_COMPLETION_REPORT.md` "Database"/"Supabase Verification" for the full, honest status.

## Alternatives considered
- Self-managed Postgres (e.g. on Railway, already used for the app's own hosting per `docs/DATABASE_SETUP.md`'s Phase 1 conventions): viable, but the brief explicitly designates Supabase for this phase; revisit only if Supabase-specific constraints (e.g. pooler prepared-statement limits, `ADR-014`) become a real operational problem.
